1. Introduction and system overview

This report documents the design, verification and characterization of an RV32IM-based microcontroller implemented on an Altera DE2-115 board. The CPU is a single-cycle RV32IM core in a Harvard organisation, with separate 8 KiB tightly coupled memories for instructions (ITCM) and data (DTCM), both realised in M9K block RAM.

Around the core sits a memory-mapped peripheral set — GPIO driving the LEDs and the six seven-segment displays, a Basic Timer with compare, PWM and input-capture modes, and an interrupt controller with a prioritised vector table. Integer division is offloaded to a dedicated accelerator that runs in a second, faster clock domain, with every crossing between the two domains protected by two-flip-flop synchronisers.

The whole design was verified in three independent ways: against a RARS golden model in simulation, against the same golden model on hardware through the In-System Memory Content Editor, and behaviourally through Signal-Tap traces captured on the board. All three agree.

2.5 Clock domains

The PLL produces two clocks from the 50 MHz oscillator: MCLK at 25 MHz for the CPU and peripherals, and DIVCLK at 150 MHz for the divider. Three signals cross from MCLK into DIVCLK (the two 32-bit operands and the DIVENA start pulse) and one crosses back (DIVBUSY); all four pass through cdc_sync, the two-flip-flop structure of the project definition's Figure 10b.

The quotient and residue cross back unsynchronised, which is safe by construction: div_stall_ctrl holds the CPU stalled until the synchronised DIVBUSY has dropped, so the result buses have long settled before the CPU samples them. This is the standard "synchronise the control, let the settled data cross" handshake, and it is why the SDC declares the two domains asynchronous — timing them against one another would report violations that the synchronisers exist precisely to make irrelevant.

4. Design decisions

4.1 BTSSEL as a clock enable, not a clock multiplexer

Figure 7 draws BTSSEL as a 4:1 multiplexer selecting between clock sources. Implemented literally on an FPGA this produces a derived clock off the global network, which fragments the clock tree and makes fmax unreportable. bt_prescaler instead generates a single-cycle tick enable at the selected rate, and BTCNT advances on that enable. The behaviour is identical; the implementation stays synthesis-clean and the whole timer remains in one analysable clock domain.

4.2 The divider in its own clock domain

A 32-cycle divider clocked at MCLK would stall the CPU for 32 cycles per operation. Running it at 150 MHz — six times MCLK — reduces that to 8 MCLK cycles, measured. On RV32IM/test1, which performs sixteen divide-class operations, this is the difference between IPC 0.50 and IPC 0.80 with an identical retired-instruction count. DIVCLK was set to 150 MHz rather than higher to leave margin under the divider's standalone ceiling of ~195 MHz.

4.3 Registering the timer interrupt event

EUQ0 is combinational over signals that settle in different delta cycles, so it emitted glitches narrower than a clock period. Figure 13 uses that line to clock the IFG flip-flop, where such a glitch latches a phantom interrupt. The event is therefore registered inside BasicTimer before it leaves the block. This was found in simulation, where a timer interval measured 7 cycles instead of 80.

4.4 Stack pointer initialisation

The benchmarks ship without a C runtime startup, so sp reset to zero. A compiled program's locals then landed near 0xFFFFFFxx, whose bits 15:14:13 are all '1' and are therefore decoded as peripheral: stack writes were discarded and stack reads returned an I/O port, so loop counters never advanced. x2 is now reset to 0x2000, the top of the DTCM. Hand-written assembly benchmarks never touch the stack, which is why this stayed hidden until the first compiled benchmark ran.

4.5 One testbench, many run scripts

The project definition names a single tb_RV32IMscMCU.vhd. Everything that differs between benchmarks — memory images, run length, board stimulus — therefore lives in the per-benchmark .do files, and the testbench leaves SW and the pushbuttons undriven for the script to force.

4.6 Producing the golden-model artefact

The DTCM is an altsyncram whose storage ModelSim ASE's mem save cannot reach. The testbench therefore mirrors the memory: it pre-loads a shadow array from the same image the hardware memory is initialised from, updates it on every committed store, and writes it out as DTCM.mem in the one-word-per-line format of the RARS golden file.

4.7 Measuring IPC without touching the architecture

A stall is, by definition, a cycle in which the PC is held. Since pc_o is already a top-level output, both IPC counters are accumulated in the testbench rather than in the design — no hardware counter was added and the architecture is unchanged. On hardware the existing mclk_cnt_o output serves the same purpose.

5. Functional verification (ModelSim)

5.1 Golden-model comparison

Of the eight supplied benchmarks only RV32IM/test1 terminates, and it is correspondingly the only one shipping a RARS post-run reference — the interactive benchmarks sit in a state-machine loop forever, so there is no end-of-run state to dump. run_rv32im_test1.do performs the comparison automatically and reports PASS on all 1024 DTCM words. The remaining seven are verified behaviourally from their waveforms.

5.2 IPC

Following LAB5 clause 6.iii.b, referenced by steps 8.c.iii and 8.e.iii:

IPC = (CLKCNT_o − (STCNT_o + 4 + depth·FHCNT_o)) / CLKCNT_o
    =  InstructionCounter / CLKCNT_o

A single-cycle core has no flushes and no pipeline fill, so this reduces to IPC = (CLKCNT − STCNT) / CLKCNT.

8. Findings

8.1 The Figure 10b synchronisers were being implemented in RAM

Inspecting the Fitter's per-entity report revealed that cdc_sync's two stages had been recognised as a shift register and mapped into two M9K blocks — Quartus had merged the three MCLK→DIVCLK instances (32 + 32 + 1 = 65 bits, 2 deep) into a single 2 × 65 ALTSYNCRAM.

This is wrong for a synchroniser. The first stage exists so that a metastable sample lands in a dedicated flip-flop and is given a full destination-clock period to resolve; a memory cell read back through an address counter does not provide that guarantee. Figure 10b draws two flip-flops, so two flip-flops is what must be built. Adding an AUTO_SHIFT_REGISTER_RECOGNITION OFF attribute to the architecture fixed it — and improved both clock domains, because the RAM lookup had been sitting on both critical paths:

8.2 Partial address decode

is_peripheral examines only address bits 15:14:13, so the 64-byte SFR window repeats 128 times across 0x2000–0x3FFF. This is a standard technique and deliberate here for timing, since the decode gates the DTCM write enable on the critical path — but it removes fault containment and was the direct cause of the stack-pointer bug in §4.4. A cleaner design would use the full comparison to qualify the peripheral chip selects only, never dtcm_we.

8.3 Benchmark constants assume a 20 MHz clock

The interrupt benchmarks hardcode timing constants for a 20 MHz MCLK. At the delivered 25 MHz, BTCTL1 = 18h selects SMCLK/8 = 3.125 MHz, so BTCMPR0 = 2,500,000 produces 0.8 s rather than the 1.000 s the source comments claim; test3's four intervals become 0.8 / 0.4 / 0.2 / 0.1 s, and test4's nominal 5 kHz PWM measures 6.25 kHz. This is a property of the benchmark constants, not of the design.

8.4 PWM duty convention

The Interrupt/test4 source comments describe the duty cycle as 2−k, which suggested a polarity conflict with Figure 8 Mode 0. The benchmark's own ReadMe resolves it: the intended sequence is 50 %, 75 %, 87.5 %, 93.75 % — that is 1 − 2−k, which is exactly (BTCL0 − BTCL1) / BTCL0, the Mode 0 formula. Figures 19 and 20 confirm it in silicon by measuring both switching points. The source comment is simply inconsistent with the ReadMe.

8.5 INTA naming

intr_fsm drives inta_o as an internal active-high acknowledge strobe, asserted during the first service cycle, rather than as the bus-level INTA drawn on page 15. The service sequence is implemented exactly as specified — two cycles, GIE cleared, TYPE captured from the data bus, source flag cleared, vector loaded and jumped to with tp holding the return address — but a reader comparing signal levels against the figure should be aware of the polarity convention.

8.6 Benchmark issues confirmed independently

Several defects identified while bringing the benchmarks up were subsequently fixed in the supervisor's revision of 29 August 2026: CAPISEL never switching to VCC, an inverted loop guard, a missing jump, BTHOLD left asserted, and a period constant that was eight times too large for SMCLK/8. Figure 18 shows the corrected capture behaviour working.

9. Conclusions

The design meets the specification. An RV32IM single-cycle core with GPIO, a Basic Timer supporting all three modes, a prioritised interrupt controller implementing the two-cycle service protocol, and a clock-decoupled division accelerator all fit in 4 % of the device and close timing at 25 MHz with 0.648 ns of margin.

The accelerator is the main architectural result. Placing the divider in a 150 MHz domain rather than clocking it at MCLK cuts the stall from 32 cycles to 8 and lifts IPC on RV32IM/test1 from 0.500 to 0.798. Because the retired-instruction count is unchanged, this is an exact comparison. The cost is 281 logic elements for the divider and 132 more for the synchronisers that make the crossing safe — around 10 % of the design for a 60 % improvement in IPC on divide-heavy code.

Frequency is limited by the memory architecture, not by logic depth. The critical path gets only half a clock period because the DTCM is negedge-clocked, as the single-cycle organisation of Figure 3 requires. The same logic would support roughly 50 MHz on a full period. Raising fmax meaningfully would therefore require pipelining — which is precisely what the bonus task asks for, and it is worth noting that the bottleneck we measured is the one that pipelining exists to remove.

Verification agreed across three independent paths. The simulated cycle count, the hardware cycle count and the RARS instruction count all reconcile on RV32IM/test1; the DTCM matches the golden model both in simulation and through ISMCE; and every peripheral behaviour observed in ModelSim was reproduced on the board, down to the input-capture value of 197 appearing identically in simulation, in a Signal-Tap trace, and in the DTCM readback.

The most instructive moment of the project was not a functional bug but a synthesis one: the Figure 10b synchronisers had been silently implemented in block RAM, which would have satisfied every functional test while quietly removing the metastability protection they exist to provide. Finding it required reading the Fitter's per-entity report rather than trusting the summary — and fixing it improved area, both clock domains, and correctness at once.
